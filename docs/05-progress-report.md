# SAHAi — Progress Report

**Status:** simulator-stage pipeline verified end-to-end. Learning not yet
demonstrated. No human-subject work begun.

This report states what has been implemented from the literature review, what
was deliberately changed and on what evidence, what remains unimplemented, and
how the training runs were actually executed.

---

## 0. Plain-language summary

We are training an AI tutor to help students solve coding problems **without
handing over the answer**. Instead of copying human tutors from a dataset, the
tutor learns by practising: it holds a conversation with a simulated student,
then we check whether that student can actually solve the problem afterwards by
running their code against tests. The tutor earns reward when the student
succeeds, and loses reward when it leaks the solution or stops acting like a
teacher.

The scoring formula is:

> **score = (did the student solve it − how good the student already was)
> − (penalty if the teaching was poor) − (penalty for leaking the answer)**

Subtracting "how good the student already was" matters: a tutor should not get
credit for a student who could already do the problem.

---

## 1. Executive summary

The system trains a tutor policy with group-relative RL against a simulated
student, rewarding the student's **execution-verified** downstream solve rate
while penalising solution leakage and non-pedagogical behaviour. The reward
follows the SAHAI formulation from the review:

```
r_SAHAI(a_T | s_T, α) = (r_sol(a_T | s_T, α) − α) + (r_ped(a_T | s_T) − 1)·λ − γ·L(a_T, α)
```

As of the last completed run the pipeline produces a non-zero gradient, the
reward discriminates leaking tutors from non-leaking ones, and every dialogue is
dumped with its reward decomposition for inspection. What it does **not** yet
show is the tutor getting better: 3 epochs × 8 rollouts is a smoke test.

## 2. What we employed from the literature review

### 2.1 Paper 1 — *From Problem-Solving to Teaching Problem-Solving* (RL for pedagogy)

| Mechanism in paper | Our implementation | Status |
|---|---|---|
| Online RL on simulated tutor↔student dialogue; no human tutoring corpus | `DialogueEngine.run()` — alternating turns, terminates on a phrase or `2 × max_turns` | **Implemented** |
| Reward at conversation level, not per turn | `SAHAIReward.compute()` scores the completed `Dialogue` | **Implemented** |
| `r_sol` = post-dialog solve rate over `K` sampled student answers | `SolveReward.compute()` calls `student.attempt_solution()` `K` times | **Implemented** (`K=4`, below the review's `K≥8` — see §4) |
| Verifiable outcome reward, not judge-scored correctness | `CodeVerifier` runs candidate code in a `subprocess` against unit tests | **Implemented** |
| `r_ped` from `M` judges, conversation accepted only if **all** accept | `PedagogyReward` holds 2 rubrics; a `RuleBasedJudge` is used on Kaggle | **Changed — see §3.1** |
| Hard penalty: `r_ped = 0 ⇒ r = −λ` | `SAHAIReward.compute()`, `hard_penalty=True` | **Implemented** |
| Actions sampled on-policy from `π_θ` | Rollouts generated by the current LoRA policy each epoch | **Implemented** |

We deliberately avoided the SFT-on-tutoring-dialogues route the paper critiques
(MathDial, SocraticLM, TutorChat). No tutoring corpus is used anywhere; the only
supervision is the student's verified downstream success.

### 2.2 Paper 2 — *Simulating Students with LLMs* (architecture review)

The review ranks simulator architectures. We implemented the one it recommends,
plus the "advanced" variant:

> *LLM + explicit memory/knowledge tracer (recommended): LLM generates language;
> a separate tracer updates mastery probabilities for each skill.*

| Mechanism | Our implementation | Status |
|---|---|---|
| LLM + explicit skill tracer | `StudentSimulator` (Qwen2.5-0.5B) + `BKTTracer` maintaining `dict[skill → mastery]` | **Implemented** |
| Injected misconceptions matching real error patterns | `MISCONCEPTIONS` — per-skill error list (e.g. `binary_search → ["wrong midpoint calculation", "infinite loop on boundaries"]`) injected into the persona prompt | **Implemented** |
| Ability-conditioned solve `r_sol(a_T \| s_T, α)` | `tracer.get_ability()` → `ability_baseline`, entering the reward as `(r_sol − α)` | **Implemented** |
| Leakage estimate `L ∈ [0,1]` | `LeakageEstimator` | **Partially — token-match only, see §4** |
| Token-match leakage heuristic | `token_match_leakage()` — overlap between tutor text and reference solution, minus Python keywords | **Implemented** |
| ACE-based leakage heuristic | `ace_leakage()` exists but is **never called with data** — training passes only `(dialogue, solution)`, so the ACE branch is dead | **Not active** |
| Combined `r_SAHAI` with `λ`, `γ` | `SAHAIReward` — `lambda_ped=1.0`, `gamma_leak=0.5` | **Implemented** |
| Code-mixed student language | `CODE_MIXING_TEMPLATES` for Hinglish / Tanglish / English; also used for the scripted opening turn | **Implemented** |

### 2.3 Paper 3 — *Why LLMs alone fall short for learner modelling*

This paper's recommendations shaped three concrete decisions:

> *Implement an explicit mastery tracker alongside the LLM tutor so decisions are
> based on interpretable skill estimates.*

Ability is **never** estimated by asking an LLM. It comes from `BKTTracer`, a
closed-form Bayesian update over per-skill mastery probabilities, updated after
each rollout via `tracer.update_batch(problem.skills, solved)`.

> *Make execution-checked post-tests your primary metric; use dialog plausibility
> only as secondary diagnostics.*

`r_sol` is a unit-test pass rate from real subprocess execution. `r_ped` is
explicitly the secondary term. We do not let a judge decide correctness.

> *Use ability conditioning and causal probes to avoid rewarding policies that
> exploit simulator quirks.*

Ability conditioning is implemented. **Causal probes are not** — see §4.

### 2.4 Paper 4 — *Deep Knowledge Tracing*

The review recommends "DKT **or** a lightweight KC tracer". We chose **BKT, not
DKT**, deliberately:

- DKT is supervised sequence prediction requiring large interaction logs
  (Khan Academy, ASSISTments scale). We have no such logs — the student is
  synthetic and every session starts cold.
- The review itself notes DKT's latent vector is "opaque (harder to map to named
  skills)". Our reward needs a scalar ability baseline `α` and our curriculum
  needs per-skill mastery for ZPD filtering. BKT gives both directly and
  interpretably.
- BKT works at `n=1` interaction; DKT would be untrainable at our data scale.

This is a scale-driven deviation, not a claim that BKT predicts better.

### 2.5 Curriculum / ZPD

`ProblemBank.zpd_sample()` draws only problems whose mean skill mastery falls in
`[zpd_low, zpd_high] = [0.3, 0.7]`, so the tutor is never trained on problems the
simulated student has already mastered or cannot approach. This operationalises
the "curriculum decisions" use the DKT paper describes for a learner model.

## 3. Deliberate deviations from the literature, and the evidence for them

### 3.1 `r_ped` is graded, not the binary all-judges-accept product

The review specifies:

```
r_ped(a_T | s_T) = ∏(m=1..M) 1[J_m(a_T, s_T) = accept]
```

We implemented this first. **It produced exactly zero gradient.**

Epoch 0 of the first run logged `loss=0.0000`. The cause is a direct interaction
between the binary reward and group-relative advantage estimation:

1. Every rollout failed at least one rubric → `r_ped = 0` for all 8.
2. `hard_penalty` mapped all of them to `r_SAHAI = −λ = −1.0`.
3. Advantage is `(r − mean) / (std + ε)`. With identical rewards, `std = 0`.
4. Every advantage became `0`. The epoch updated nothing.

This is a structural incompatibility, not bad luck: the paper's binary `r_ped`
was designed for **PPO with a learned value baseline**, which tolerates constant
rewards. GRPO has no value network — within-group reward variance *is* the
entire learning signal, so a binary conversation-level reward collapses it
whenever `G` is small.

We changed `RuleBasedJudge.evaluate()` to return the **fraction of checks
passed**. Measured effect: reward spread went `0.000 → 1.317` and epoch-0 loss
`0.0000 → 0.0562`.

The `hard_penalty = −λ` rule from the paper is **retained** — it now fires only
when a dialogue fails every check, which is its intended meaning.

### 3.2 GRPO instead of PPO

The paper uses PPO. We use group-relative advantages with no critic, which
halves memory on a 16GB T4 and removes value-function tuning.

**Stated honestly:** `clip_epsilon` exists in settings but is unused. The update
is currently REINFORCE with a KL penalty to a frozen reference (LoRA adapters
disabled), not clipped PPO-style GRPO. This should not be described as clipped
GRPO in any writeup until the ratio term is added.

### 3.3 Rule-based judge instead of `M` LLM judges

The review recommends multiple judge families with one held out, to prevent
judge-gaming. Both LLM rubrics are implemented in `RUBRICS`, but the Kaggle
config sets `num_judges=0, use_rule_judge=True` — a third model would not fit
alongside the tutor and student on one T4.

**Consequence to acknowledge:** the current `r_ped` is a five-check heuristic
(no code blocks, no solution patterns, asks questions, reasonable length, no
dangling promises). It is gameable in ways an LLM judge would not be, and the
judge-holdout protection from the review is absent.

## 6. Results

| Epoch | loss | reward | solve | ped | leak | reward spread |
|---|---|---|---|---|---|---|
| 0 | 0.0562 | −0.644 | 0.063 | 0.781 | 0.375 | 1.317 |
| 1 | 0.0367 | −0.790 | 0.000 | 0.625 | 0.304 | 0.600 |
| 2 | 0.2143 | −0.752 | 0.031 | 0.656 | 0.403 | 1.159 |

Held-out (20 MBPP problems): `solve_rate 0.000`, `ped_acceptance 0.688`,
`leakage_rate 0.126`.

### What the run does support

- **The pipeline produces a learning signal.** Non-zero reward spread in every
  epoch, hence non-zero advantages and non-zero loss. This was the run's purpose.
- **The reward discriminates leakage as intended.** Rollouts where the tutor
  wrote code average `−1.045`; rollouts where it did not average `−0.503`.
- **`r_sol` is genuinely execution-verified.** The notebook asserts the verifier
  reproduces a known-good MBPP solution at `1.0` before training starts.

### What it does not support

- **No claim of learning.** 24 dialogues and 3 optimizer steps cannot separate
  signal from noise. `ped` moving `0.781 → 0.625 → 0.656` is sampling variation.
- **`solve` is uninformative.** With `K=4` over 8 rollouts it is quantised to
  1/32; the observed values are one or two lucky passes.
- **`leak` is not comparable across systems.** The estimator does not exclude
  problem-statement tokens, so it has a high floor.

### Behavioural findings from the transcripts

Measured over all 172 turns of the run:

| | tutor | student | intended |
|---|---|---|---|
| turns containing code | 14% | 18% | 0% / 0% |
| turns asking a question | 37% | 16% | ~100% for tutor |
| mean words per turn | 66 | 56 | student: 1–2 sentences |

**The roles invert.** The dominant mechanism was identified and quantified: 19%
of turns end on a dangling colon (`"Here is the implementation:"`), which invites
the next speaker to fulfil the promise rather than reply to it. In 5 of 24
dialogues the student answered the problem outright in its opening turn.

Countermeasures now implemented, unverified until the next run:

- Opening student turn scripted from the persona's code-mixing templates.
- Trailing-colon clauses trimmed from student turns.
- A fifth pedagogy check penalises the tutor for dangling promises — the tutor
  cannot be post-processed, because it is the policy under training and editing
  its text would compute log-probs over tokens it never sampled.

## 7. Next steps

1. **Verify the role-inversion fix** — re-run and check the turn statistics above.
2. **Wire ACE.** Randomized hint withholding in 10–20% of rollouts, feeding
   `solve_with` / `solve_without` into `LeakageEstimator.estimate()`. This is the
   review's central causal probe and is currently dead code.
3. **Fix the leakage denominator** — exclude problem-statement tokens so `L` is
   interpretable in absolute terms.
4. **Scale.** Raise `group_size` before `epochs`; larger groups are what prevent
   advantage collapse. Raise `K` to ≥8 per the review.
5. **Add the importance ratio and clipping**, so the method is what it is called.
6. Only then consider the pre-registered sim→real pilot.
